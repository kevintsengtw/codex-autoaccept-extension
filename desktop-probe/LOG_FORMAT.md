# 0.3.10 本機 log 格式

正常 ON 使用即記錄，不需要切換診斷模式。設定視窗的「開啟本次 log 摘要」開啟短摘要，完整階段另存於同名主檔。新後端連接建立新檔，舊檔保留在 `%LOCALAPPDATA%\CodexUiaProbe`。

完整原因與核准前後階段保留在本機，不要求停住工作或手動抄寫。以下為格式示例，並非公司測試結果：

```text
回報碼：0310-BX-S05
結果：找到按鈕，但按鈕座標為空或無效
```

回報碼格式為 `0310-視窗狀態-階段原因`。0.3.9 的歷史檔使用 `039`，閱讀時應依該檔版本辨識，不改寫既有 log。摘要先列歷史受阻／錯誤、最近一次核准嘗試和各視窗狀態的最後掃描；詳細紀錄只供本機後續查看。後續恢復不刪除歷史紀錄；歷史錯誤不表示現在仍失敗。

相同掃描狀態與等待前候選／結果的事件會合併；上筆紀錄滿十秒後，在下一次完成掃描或等待事件留下新一筆。開 ON 後首筆掃描也重新記錄。這是紀錄節流間隔，provider 卡住時不保證每十秒有新紀錄；沒有新筆不能直接認定請求不存在、後端退出或 renderer 停止。逐案測試仍需獨立保存真實請求確認、計時、視窗條件及 marker。

| 視窗狀態 | 意義 |
| --- | --- |
| FX / FN | 最大化／一般大小，位於前景 |
| BX / BN | 最大化／一般大小，位於背景 |
| M | 最小化 |
| U | 無法確認，或屬於開關／啟動事件 |

背景由前景 HWND 判斷，不含遮蔽百分比；桌面不可確認不能直接判定鎖定。核准事件使用本次或最後重掃的狀態，並非核准瞬間所有屬性的原子快照。

| 階段原因 | 中文意義 |
| --- | --- |
| S00 | 本次完整掃描沒找到「允許一次」Button；不能判定當時有待核准請求 |
| S01 | 找到符合條件的候選；只代表掃描，不代表呼叫核准 |
| S02 / S03 | 按鈕未啟用／App 未提供 Invoke |
| S04 / S05 / S06 / S07 | 條件未通過／座標無效／中心不在目標範圍／前景按鈕不可見 |
| Bxx / Rxx | 視窗條件阻擋／掃描或驗證未完成；結果行直接寫明原因 |
| E10 / E11 / E12 | 目標視窗／根元素／按鈕祖先鏈變動 |
| E13 / E14 / E15 | 按鈕條件／局部內容／Invoke 能力變動 |
| E17 | 核准前重掃未取得候選；附當次重掃的中文結果與碼 |
| A01 | 已承諾開始一次核准嘗試，還沒有確認結果 |
| A02 | Invoke 返回；不能單憑返回認定 App 工作繼續 |
| A03 | 自動模式下原候選本身的讀取失效，工具結束本次觀察；不含根元素或 WindowPattern 讀取失敗 |
| A04 | 原核准按鈕在前景下隱藏，工具結束本次觀察；不以背景或最小化的不可見屬性判定完成 |
| A08 | 核准呼叫返回後的原生視窗狀態；轉為前景不代表全程背景成功 |
| L01 | 主 log 附加失敗；停止新嘗試，不重送可能已生效的核准 |
| L02 / L03 | 摘要暫存寫入／原子取代失敗；原因與 Win32 檔案錯誤代碼記入主 log，繼續監聽，摘要可能過期 |
| A05 | 前一候選尚未離開或同一候選已處理，不重送 |
| A06 / A07 | 結果未確認／嘗試開始後錯誤，可能已生效，不重送；A07 附固定中文失敗階段 |
| T01 / T02 / T03 | 初次掃描／核准前重掃／核准或觀察逾時 |
| G01 / G02 | ON／OFF 或開關已改變 |

`Bxx`、`Rxx` 的尾碼：00 其他讀取、01 原生狀態、02 隱藏、03 系統 cloak、04 互動桌面、05 根視窗狀態、06 frame、07 modal 阻擋、08 掃描中切換、09 根元素讀取、10 WindowPattern、11 控制項屬性、12 父層／局部內容、13 節點上限、14 深度上限、15 樹重複、16 多候選。結果文字會直接說明原因。

R12 掃描上限修正版另以 R13 記錄「擴大上限，下輪從根元素完整重掃」或「已達最高上限，本輪拒絕核准」，附 UIA／MSAA、初掃／重驗及舊／新上限。這是未完整掃描的紀錄，不代表已核准。預設系統匣自動模式依序使用 3000、6000、10000，達最高上限仍不完整時保留 ON 等待；沒有清除未知核准的去重狀態。重複的最高上限訊息仍按十秒合併，provider 卡住時不保證固定輸出頻率。

A07 的失敗階段只取固定值：核准前原生視窗狀態查詢、Invoke 呼叫、Invoke 返回後原生視窗狀態查詢、呼叫返回階段紀錄、核准後結果觀察；未知值寫「未確認」，不寫原始例外內容。A01 是承諾開始一次嘗試，仍須查看是否實際進入 Invoke，不能以 A07 斷定呼叫已生效。

0.3.10 將核准後觀察的根元素與 WindowPattern 讀取移出原候選失效的例外處理區塊。這些讀取失敗會記 A07「核准後結果觀察」，保留結果未知與等待舊候選離開的狀態，不產生 A03、不結束未知週期，也不重送 Invoke。切 OFF／再次 ON 只改變開關代次，不清除已開始嘗試的未知候選。其後必須由既有完整掃描與週期界線確認，才能開始新嘗試。A03、A04 本身仍不是 App 工作完成證據，須另外核對 marker 與後續工作；手動模式的 A03 也可能表示原按鈕不可用或隱藏，須依結果文字辨識。

L01–L03 包含 I/O、拒絕存取及安全性例外。只有 HRESULT 明確屬於 Win32 facility 時才記其錯誤碼，其他情況寫「未確認」。短摘要失敗後先將固定原因附加主檔，再繼續；主檔寫入失敗則停止新嘗試。不同檔案錯誤碼保留為不同原因，不重試主檔附加或核准呼叫。

完整紀錄中每筆有 L 序號和 P 候選編號。P 只是在同一後端執行期間，依 UIA 候選識別與可觀察的離開週期建立的本機序號，不是 App 原生請求 ID；UIA 重用元素或缺少離開訊號時無法可靠區分每次業務請求。沒有候選就明確標示未建立關聯，不把先前 P 編號套到未知工作。

log 僅含工具固定文字、本機時間、視窗狀態和有界計數。命令、對話、標題、PID、路徑、UIA RuntimeId 與局部內容指紋不寫入。這項紀錄改造不代表完全遮蔽、最小化或鎖定問題已修復。
