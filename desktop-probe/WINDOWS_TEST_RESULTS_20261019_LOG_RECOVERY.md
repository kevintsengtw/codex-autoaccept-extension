## 重現與修正

修正前，在 Windows 以 `FileShare.Read` 暫時開啟合成主 log，180 毫秒後解除占用；既有 `LocalLogWriter.Append` 立即拋出 `MAIN_APPEND / Win32 32`，重現程式退出碼為 1，未達預期的自動恢復。這證明一條可重現的失敗路徑，不是公司根因的證明。原始輸出 `evidence/reproduction-before.txt`、時間及退出碼 JSON、原始碼副本均保留。

修正改為分開開檔與寫入：只有未寫入的 `MAIN_OPEN` 遇到 IOException 且 Win32 為 32／33，才最多嘗試五次、間隔 100 毫秒。成功後只執行一次寫入；其他錯誤與用盡次數仍停止。開始寫入後即使遇到相同錯誤碼，也不重開或重寫；flush 失敗亦不重播。原本的核准前紀錄、OFF 代次、唯一候選、完整重驗與去重規則保持不變。

後端送出固定且有界的 `LOG_WRITE_DIAGNOSTIC` 資料，包含實際事件時間、毫秒、UTC offset、階段、Win32 碼及嘗試次數。前端同步驗證並另存於 `%LOCALAPPDATA%\CodexAutoAcceptDesktop\diagnostics`，不依賴已故障的主 log。摘要失敗先保存 WARNING；若接著主檔警告也失敗，另保留 FAILURE。診斷位置也無法寫入時，介面保留錯誤資料並明示保存失敗，不宣稱已落盤。重新連接另開新檔，不覆寫前一輪。

介面的停止訊息增加失敗時間、階段與 Windows 碼，按鈕優先開啟本次獨立失敗診斷；無診斷檔時改開完整主 log。文字區增高以容納欄位，其他控制項順移，不增加 App 操作或啟動旗標。

本機 Windows `10.0.26300`，.NET SDK `10.0.402`；產品目標 net48，既有十一組測試目標 net8.0。套件使用隔離的三個既有公開套件快取，鎖定檔不變；`RestoreSources` 指向空的本機來源，`NuGetAudit=false`，因此沒有進行套件弱點資料查詢，不把它列為通過項目。

